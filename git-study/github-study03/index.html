Git 브랜치와 병합

브랜치란?

브랜치는 메인 작업에서 가지를 쳐서 별도 방향으로 작업할 수 있게 해줍니다.

머리에 가지가 뻗어나가는 나무를 상상하세요.

master        HEAD → like_feature
c1 — c2              (new branch)

like_feature   HEAD → master
c1 — c2 — c3   (merged back)

브랜치 만들기와 전환

# 새 브랜치 생성 (현재 상태 그대로 복사됨)
git branch like_feature

# 브랜치 목록 확인
$ git branch
   like_feature
* master           # *가 현재 있는 브랜치

# 브랜치 전환 (checkout)
git checkout like_feature
Switched to branch 'like_feature'

# 생성과 전환을 한 번에
git checkout -b feature/login

브랜치는 스냅샷의 다른 라벨일 뿐입니다.

새로운 파일이 생기는 게 아니라, 같은 내용을 가리키는 이름이 늘어나는 것입니다.

Fast Forward Merge

기본 병합 흐름

# 1. feature 브랜치에서 작업 완료 후 master로 전환
git checkout master

# 2. merge (fast-forward 방식)
$ git merge like_feature
Updating d78ade4..a63hec2
Fast-forward
 comment.js | 3 ++-
 1 file changed, 2 insertions(+), 1 deletion(-)

Fast Forward는 master의 커밋이 nothing_changed일 때 발생합니다.

브랜치의 커밋을 master로 “당겨오기” 때문에 병합 커밋이 생성되지 않습니다.

가장 깔끔한 방식입니다.

Fast Forward가 아닌 경우

master에 새 커밋이 있으면 자동으로 3-way merge가 발생합니다.

$ git log --graph --all --pretty=oneline
* c3360a...(HEAD->master) add master
| * 782d90...(like_feature) add like_feature
|/
* 1c7881... init git

# merge 수행
$ git checkout master
$ git merge like_feature
[main] update#setState idle
Merge made by the 'recursive' strategy.
 checkout.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

결과: 병합 커밋이 새로 생성됩니다.

c3 (HEAD->master)
/
c5 ← merge commit
 \    \
  c4   c2
   \   /
    c1

Merge Conflict — 충돌 처리

충돌이 발생하는 경우

두 브랜치가 같은 파일의 같은 부분을 다른 내용으로 수정했을 때 발생합니다.

$ git merge like_feature
Auto-merging comment.js
CONFLICT (content): Merge conflict in comment.js
Automatic merge failed; fix conflicts and then commit the result.

충돌 해결 방법

1. 수동으로 파일에서 conflict 표시 제거

<<<<<<< HEAD          // ← 현재(master)의 버전
$(".comment-good").text($(".comment-good").val()-1);
=======              // ← 병합하려는(branch) 버전
$(".comment-good").text($(".comment-good").val()-1 < 0 ? 0 : $(".comment-good").val()-1);
>>>>>>> like_feature   // ← 병합 끝 표시

위에서 <, =, > 기호를 찾아서 불필요한 부분을 삭제하고 원하는 내용으로 수정합니다:

// ✅ 충돌 해결 후 (두 버전 중 선택 또는 조합)
$(".comment-good").text(
    $(".comment-good").val() - 1 < 0 ? 0 : $(".comment-good").val() - 1
);

2. git status로 충돌 파일 확인

$ git status
On branch master
You have unmerged paths.

   (fix conflicts and run "git commit")

Unmerged paths:
   (use "git add <file>..." to mark resolution)
       both modified:  comment.js

3. 충돌 해결 후 커밋

git add comment.js    # 충돌 해결 파일 추가
git commit -m "Merge branch 'like_feature' — resolve conflict"

충돌을 완전히 피하는 방법

전략설명
작은 브랜치한 브랜치가 다루는 범위가 작을수록 충돌 확률 감소
자주 master에 merge오래된 브랜치를 자주 병합하면 변경 범위 예측 가능
.gitignore 활용빌드 산출물, 로그 등은 버전 관리하지 않음

브랜치 정리

# 이미 병합된 브랜치 확인
$ git branch --merged
   like_feature           # ✅ master에 merge됨 — 삭제 안전
* master

# 브랜치 삭제 (병합 완료된 브랜치)
git branch -d like_feature
Deleted branch like_feature (was 782d90).

# 강제로 삭제 (아직 병합 안 됨)
git branch -D like_feature

-d (소문자)는 병합된 브랜치만 삭제합니다. 안전 장치입니다. -D (대문자)는 강제 삭제 — 내용 손실 가능.

HEAD Detached State

git checkout로 특정 커밋 해시에 이동하면 detached HEAD 상태가 됩니다.

이 상태에서 한 것은 임시 작업일 뿐, 브랜치에 반영되지 않습니다.

$ git log --pretty=oneline
e4abb6f... (HEAD -> master) this is master
d97d387... another snapshot

$ git checkout d97d38
HEAD is now at d97d38 another snapshot

# detached 상태 — 원하면 브랜치로 만들어서 저장
git checkout -b old-snapshot d97d38

Git Internals — Git 내부 구조 이해

Git이 어떤 객체들로 이루어져 있는지 이해하면 병합 전략이 훨씬 명확해집니다.

핵심 객체

객체역할파일 형식
Blob파일 내용 (압축)git/objects/{2자}{38자}
Tree폴더 구조 (블러브 + 하위 트리를 참조)동일
Commit스냅샷 + 메타데이터 (author, date, parent)동일
Tag커밋에 이름 붙임 (버전 표시)동일

SHA-1 해시 확인

# 객체 타입 확인 (commit, tree, blob 등)
git cat-file -t <SHA-1>

# 객체 내용 보기
git cat-file -p <SHA-1>

왜 브랜치 전략이 중요한가?

  1. 실험 안전성: 버그 수정, 새로운 기능 등을 별도 공간에서 시도 — 메인에 영향 없음
  2. 동시 개발: 여러 팀원이 동시에 다른 기능 개발 가능
  3. 코드 리뷰 용이: 작은 브랜치별로 diff를 보면 리뷰하기 쉬움
  4. 릴리즈 관리: release 브랜치에서 QA → main으로 배포하는 프로세스
