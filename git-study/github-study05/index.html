1. Git Internals 복습

Git의 4가지 핵심 객체

객체역할내용

2. Pull Request (PR) / Merge Request (MR)

PR/MR란?

원격 저장소에서 브랜치 간 변경 사항을 병합하기 위한 협업 도구입니다.

Developer A              Reviewer B              Repository
    │                       │                        │
    │── feature/login ──→   │── PR 생성 ─────────→  GitHub/GitLab
    │                       │                        │
    │                       ├── 코드 리뷰 ──────────→  Comment/Review
    │                       │                        │
    │                    ✔ Approve ──────────────→  Merge (Squash)
    │                       │                        │
    Main branch 업데이트 ◄── merge 완료 ◄──────────  main 브랜치 병합

PR 작성 체크리스트

항목설명
제목feature/login-api 또는 bugfix/404-error 형식
설명왜 변경했는지, 어떤 영향을 미치는지
관련 이슈Issue 번호 링크 (#123)
스크린샷/GIFUI 변경 시 시각적 증거 첨부
Checklist[ ] 테스트 통과, [ ] lint 통과 등

병합 전략 선택

전략설명언제 쓰면 좋을까?왜 쓰지 않아야 할까?
Merge Commit두 브랜치를 그대로 합침 (병합 커밋 생성)브랜치 역사가 중요한 대형 프로젝트히스토리가 지저분해질 수 있음
Squash and Merge모든 커밋을 하나로 압축깔끔한 히스토리 유지, 작은 기능 단위세분화된 변경 이력 손실
Rebase and Merge커밋들을 직렬로 재배치선형적인 히스토리 선호충돌 해결이 번거로울 수 있음

GitHub 설정에서 PR 병합 정책 선택

GitHub → Settings → General → Pull Requests에서 기본 병합 전략을 설정할 수 있습니다.

팀의 워크플로우에 맞게 Squash를 기본값으로 권장합니다.

3. Git Flow — 브랜치워크플로우 표준

Git Flow (2010년 Vincent Driessen 제안)

master (release)        ────────────●───────●───────▶
              │                  ╱        ╲
release          ───╳───────╳─╱            ╲
       │           ╱      ╱                 ╲
develop        ●──╳─────╳─╱                   ●──▶
     │         ╱   ╲  ╱  ╱
feature       ╱    ╲╱  ╱
hotfix        ●─────●──────────────────────────▶

주요 브랜치: master, develop
작업 브랜치: feature/*, release/*, hotfix/*

브랜치 전략별 접두사

접두사용도예시
feature/새 기능 개발feature/login-api
bugfix/버그 수정bugfix/cart-quantity
hotfix/긴급 수정 (main에 직접 반영)hotfix/server-latency
release/릴리즈 준비/QArelease/1.2.0
experiment/실험적 기능experiment/new-auth
docs/문서 수정docs/api-update

커밋 메시지 컨벤션

{type}: {short description} #{issue-number}

feature/login-api-api        #45      (새 로그인 API 구현)
bugfix/cart-quantity-bug     #102     (장바구니 수량 오류 수정)

release/1.2.0                (v1.2.0 릴리즈 준비)
docs/api-update              #88      (API 문서 갱신)

4. Git LFS — Large File Storage

왜 Git에서 대용량 파일이 문제인가?

Git은 모든 버전의 파일 내용을 저장합니다.

이미지, 동영상, 모델 파일 등이 커밋에 포함되면:

문제점설명
저장소 폭발파일이 작아도 매번 전체 스냅샷을 저장 → 용량 급증
느린 클론/푸시대용량 파일을 매번 전송해야 해서 속도가 극도로 느려짐
협업 병목팀원마다 수십 GB를 받아야 함

Git LFS란?

Large File Storage — 대용량 파일을 Git 객체가 아닌 별도 서버에 보관하고, 로컬에는 포인터 파일만 저장하는 확장입니다.

# 일반 Git: 실제 파일 내용이 커밋에 포함됨
commit a34cde... → blob(50MB 이미지)

# Git LFS: 포인터 파일만 저장, 실제 파일은 별도 서버
commit a34cde... → pointer_file(28bytes)  ←→ remote server의 실제 파일(50MB)

어떤 파일에 LFS를 사용해야 하는가?

LFS 사용하는 것이 좋은 파일LFS 불필요한 파일
.mp4, .mov (동영상)텍스트 코드 파일
.psd, .ai (포토샵/일러스트)JSON/XML 설정 파일
.zip, .tar.gz (압축)작은 이미지 (.png, .gif)
.csv, .parquet (데이터셋)소스 코드
학습된 모델 파일 (.pth, .pt, .h5)텍스트 문서 (.md)
폰트 파일config 파일

Git LFS 기본 명령어

# 1. Git LFS 설치
git lfs install

# 2. 추적할 파일 패턴 지정 (.gitattributes 자동 생성)
git lfs track "*.psd"
git lfs track "*.mp4"
git lfs track "*.csv"
git lfs track "*.pth"

# .gitattributes에 다음과 같이 자동 기록됨:
# *.psd filter=lfs diff=lfs merge=lfs -text
# *.mp4 filter=lfs diff=lfs merge=lfs -text

# 3. 일반 커밋/푸시 (LFS 파일은 포인터만 push, 실제 파일은 별도 LFS 서버에)
git add .
git commit -m "Add trained model"
git push        # ✅ 일반 git push로 끝!

# 4. 파일 다운로드 (clone/pull 시 자동 포함)
git lfs pull

# 5. 관리 명령어
git lfs ls-files    # 현재 추적 중인 LFS 파일 확인
git lfs status      # LFS 관련 상태 보기
git lfs prune       # 사용되지 않는 로컬 캐시 정리

Git LFS vs Submodule vs Git Annex 비교

구분Git LFSGit SubmoduleGit Annex
용도대용량 파일 관리다른 레포지토리 참조분산 대용량 관리
학습 곡선낮음 ( git lfs push)중간높음
GitHub 호환✅ 완전 지원✅ 부분 지원❌ 별도 설정 필요

GitHub LFS 요금

  • 무료: 1GB 저장 + 1GB대역폭/월
  • 추가 사용 시: GB당 $1/월

CI/CD 파이프라인에서 LFS를 사용할 때는 반드시 git lfs pull을 실행해야 합니다.

자동으로 다운로드되지 않으므로 파이프라인에 명시적으로 포함시켜야 합니다.

5. Git 고급 명령어 모음

Git Stash — 작업 일시 중단

현재 변경 사항을 잠시 저장했다가 나중에 다시 적용합니다.

# 현재 작업을 stash에 저장 (스태싱 영역 포함)
git stash save "메시지"          # 메시지를 붙여서 스테이션

# 스테이션 목록 확인
$ git stash list
stash@{0}: On master: WIP login feature
stash@{1}: On develop: hotfix crash bug

# stash를 적용하되 stash에서 제거 (pop)
git stash pop                    # 최신 stash 적용 + 제거

# stash를 적용하되 stash에 남김
git stash apply                  # 스테이션 적용 but 유지

# 특정 stash 번호로 접근
git stash apply stash@{1}

# 모든 stash 삭제
git stash clear

stash는 임시 저장소입니다.

장기 보관용이 아닙니다.

반드시 git commit으로 커밋하거나 git branch로 브랜치에 저장하세요.

stash가 사라져도 recover할 수 있는 git reflog가 있지만, 복잡합니다.

Git Tag — 버전 표시

릴리즈 시점에 이름을 붙입니다.

CI/CD 파이프라인과 연동해서 자동 배포에 활용합니다.

# 태그 생성 (로컬)
git tag v1.0.0

# 태그 푸시 (원격 저장소에 공유)
git push origin v1.0.0

# 태그 목록 확인
$ git tag
v0.9.0
v1.0.0

Git Cherry-Pick — 특정 커밋만 가져오기

다른 브랜치에서 특정 커밋 하나만 현재 브랜치로 복사합니다.

Hotfix에 가장 유용합니다.

# 다른 브랜치의 특정 커밋 해시 확인
$ git log --oneline
a1b2c3d add login page
e4f5g6h hotfix: fix crash on startup

# 현재 브랜치로 cherry-pick
git cherry-pick e4f5g6h

Git Reflog — HEAD 이력 추적

HEAD가 어디로 이동했는지 전체 기록입니다.

실수로 git reset해서 커밋을 잃어버렸어도 recover할 수 있습니다!

$ git reflog
a1b2c3d HEAD@{0}: commit: fix crash
e4f5g6h HEAD@{1}: checkout: moving from hotfix to main
9876543 HEAD@{2}: reset: moving to HEAD~2
...

# 잃어버린 커밋 recovery
git reset --hard a1b2c3d   # recover 가능!

Reflog를 언제 쓰면 좋을까? 실수로 삭제한 브랜치나 커밋을 되찾을 때. 언제 쓰지 않아야 할까? 일상적인 작업에서는 reflog에 의존하지 마세요. 모든 변경은 commit으로 남기는 것이 원칙입니다.

Git Bisect — 이진 탐색으로 버그 찾기

어느 커밋에서부터 문제가 생겼는지 이진 탐색으로 찾아줍니다.

수백 개 커밋 중 하나를 찾을 때 빛을 발합니다.

# bisect 시작 (현재 = bad, 오래된 태그 = good)
git bisect start
git bisect bad                     # 현재가 버그 발생 상태
git bisect good v1.0.0             # 이 때는 괜찮았음

# 자동으로 중간 커밋으로 이동 → 다시 good/bad 지정 반복
# 약 log₂(커밋수) 단계로 끝남 (500개 커밋이면 9단계!)

# 탐색 완료
git bisect reset                   # 원래 위치로 돌아옴

Bisect를 언제 쓰면 좋을까? 어느 시점부터 버그가 생겼는지 모르지만 good/bad 기준점이 있을 때. 언제 쓰지 않아야 할까? 문제가 분명하게 보이는 경우나 테스트 파일이 없는 경우엔 비효율적입니다.

6. GitLab CI/CD 기초

Pipeline 개념

Pipeline (전체 파이프라인)
├── Stage: Build (빌드 단계)
│   └── Job: compile      ← Docker 실행
├── Stage: Test (테스트 단계)
│   └── Job: run_tests    ← 테스트 실행
└── Stage: Deploy (배포 단계)
    └── Job: deploy_prod  ← 서버 배포

주요 구성 요소

용어설명
PipelineCI/CD 전체 흐름 (스태디드 → 테스트 → 배포)
Stage파이프라인의 단계 (빌드, 테스트, 배포 등)
Job스테이지 안의 개별 작업 (Docker 컨테이너 안에서 실행)

GitLabRunner 설정 (예시)

# Docker 확인
docker ps

# 로그 확인
docker logs <gitlab-runner-containter-id>

Personal Access Token (PAT)

GitLab에서 HTTPS로 clone/pull/push할 때 사용하는 인증 토큰입니다.

2년마다 갱신해야 합니다 (GitLab 정책).

  • PAT는 개인.access token으로 GitHub/GitLab 계정 설정에서 발급받습니다.
  • 코드에 절대 포함하지 마세요 (git push 시 git-secrets 등 lint로 검사됨)
  • 필요 없으면 즉시 Revoke하세요

7. GitLab 프로젝트 생성 단계

  1. Project 생성: New project → Create blank project
  2. 이름/슬러그 설정: 프로젝트 URL의 일부가 됨
  3. 네임스페이스 선택: 개인 계정 or 조직 그룹
  4. Visibility 설정
    • Private: 본인만 접근
    • Internal: 조직 내부만 접근
    • Public: 모두 공개
  5. README 초기화: 프로젝트 설명과 시작 가이드
